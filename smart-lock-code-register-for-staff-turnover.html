A Smart Lock Code Register That Survives Staff Turnover

Published by Eyonic CCTV.

A practical guide for Sarawak premises managers on keeping a smart lock code register that ties every PIN or user slot to a named holder and a removal date, so staff turnover does not leave live codes behind.

Why a Code Register Matters More Than the Lock Itself

A smart lock is a small computer attached to a door. It remembers users, slots, PINs, cards and sometimes a phone app account. When someone leaves, the lock does not know. It keeps accepting whatever credential that person was given until a human removes it. That is the whole reason a register exists: the lock stores credentials, but only the register stores accountability.

This guide is written for premises managers in Sarawak who are planning an ordinary security project and have been asked, or have decided, to keep a written record of who holds which code. It is not a review of any particular lock and it does not assume a specific brand. It is a template and a workflow you can adapt to whatever hardware is on your door.

One useful framing comes from Eyonic's own product notes: smart lock door access is good for controlled convenience when user permissions and backup entry are planned properly. That sentence is the design brief for the register. Permissions and backup entry are exactly the two things a register records and a turnover event tests.

The register is not a security system by itself. It is the document that makes the system auditable. Without it, a lock with twenty user slots is a lock with twenty unknowns.

What the Register Should Hold

Keep the register as a single table, either on paper in a locked drawer or in a shared file with edit history. A spreadsheet is fine; the point is that it is one authoritative copy, not three partial lists in different inboxes.

Suggested columns, as an author heuristic rather than a standard:

User number or slot. The lock usually numbers its users. Record the number the lock actually uses, because that is what you will see when you open the admin menu.

Holder name and role. A real person, not a department. "Operations" cannot be asked to return a credential.

Credential type. PIN, card, fob, phone app, or a mechanical key held in a safe. Different types have different removal steps.

Issue date and who issued it. The person who handed over the credential should be named, so the record has an owner.

Planned removal date or trigger. "On last working day" or "on role change" or a specific date. A register without a removal trigger slowly becomes a list of former staff.

Backup entry method. Note whether this holder also holds the mechanical override key or the backup code, and where that backup is kept.

Removal confirmed date and by whom. The most important column, and the one most often left blank.

Notes. Lost card, damaged fob, temporary contractor, and so on.

If the lock supports schedules or time-limited access, add a column for the schedule name. A code that only works during office hours is a different risk from a code that works at midnight, and the register should show which is which.

Matching the Register to the Door and the Role

Before you write a single row, decide what kind of access the door actually needs. Eyonic's review note makes the point that smart locks work best when the door condition, user roles and backup method are reviewed before installation, and that for business use the question of whether a standalone smart lock or an access-control panel is more appropriate is usually checked first. That is a sensible order, and it changes what the register looks like.

A standalone smart lock on a small office door might have a handful of users and one admin PIN. The register can be one page. A door with an access-control panel and many cardholders needs a register that can be filtered by role, because the list will be long and the removal steps differ.

Door condition matters too. A register entry that says "backup: mechanical key in reception safe" is only true if the door actually has a working mechanical override and the key is actually in that safe. Write down what you verified, not what you assumed.

User roles should drive the columns you fill in. A cleaner who needs the door open before opening hours has a different removal trigger from a manager with full admin rights. If the register treats every holder the same, it will under-manage the admin accounts, which are the ones that matter most.

This is also the point to decide who holds admin rights. Two named people is a common arrangement; one is fragile, and many is unaccountable. Whatever you choose, record it in the register header so a new manager can see the rule.

The Change-of-Staff Workflow

Turnover is not a single event. It is a sequence, and the register should follow the sequence. The following steps are a suggested workflow, not a certified procedure.

Step one, before the last day. The holder's manager confirms the last working day and tells whoever administers the lock. Put the planned removal date in the register while the person is still there to hand things back.

Step two, on the last day. Collect physical credentials: cards, fobs, and any mechanical key. Count them against the register row. If a card is missing, record that in the notes column rather than leaving the row clean.

Step three, remove the credential from the lock. Delete the user slot or disable the account, then test that the credential no longer opens the door. A deletion that was not tested is a hope, not a removal.

Step four, close the row. Enter the removal date and the name of the person who did it. If the holder also had a phone app account, record that it was revoked, because app access is easy to forget.

Step five, review the backup. If the leaver was one of the people who knew where the mechanical override key is kept, consider whether the hiding place or safe combination should change. Record the decision either way.

Step six, monthly sweep. Once a month, read the register for rows with a planned removal date in the past and no confirmed removal. Those are the rows that matter. A short sweep is more useful than a perfect template that nobody opens.

Contractors, Temporary Staff and Shared Codes

The hardest rows in any register are the temporary ones. A contractor working for two weeks, a relief staff member covering a public holiday, a cleaner from an agency: each needs access, and each is easy to forget.

Give temporary holders their own rows, never a shared code. A shared code destroys accountability, because the register can no longer say who held it. If the lock has limited user slots, that is a reason to plan the slot count before installation, not a reason to share.

Set a removal date at the moment of issue. A temporary row with a blank removal date is a permanent row in disguise.

For contractors, record the company name as well as the individual, and note who sponsored the access. When the contract ends, the sponsor is the person you ask.

If a code must be shared for a genuine operational reason, such as a delivery arrangement, record it as a shared credential with the names of everyone who knows it, and plan to change it when any one of them leaves. Shared credentials should be the exception, and the register should make that visible.

A Worked Example: A Small Shop in Sarawak

The following is a fictional example, used only to show how the register reads in practice.

A small shop has one smart lock on the staff entrance. The register header records two admin holders, the shop manager and the owner, and states that the mechanical override key is kept in the owner's safe.

Row one: manager, PIN, issued in January, removal trigger "on leaving role", backup key holder noted as no. Row two: owner, phone app plus PIN, admin, backup key holder noted as yes. Row three: senior staff, card, issued in February, removal trigger "on leaving role". Row four: relief staff, PIN, issued for a two-week cover period, removal date set at issue. Row five: cleaning contractor, card, issued for a three-month contract, sponsor recorded as the manager.

When the relief staff member finishes, the manager deletes the PIN, tests the door, and closes row four with a date. When the cleaning contract ends, the manager collects the card, removes it, and closes row five. The monthly sweep finds nothing outstanding, which is the point.

Now imagine the manager leaves without warning. The register still shows that row one is open, that the manager held a PIN, and that the owner holds the backup key. A new manager can act on that. Without the register, the new manager would be guessing which of the lock's user slots belonged to whom.

Where the Register Sits in the Wider Security Plan

A code register is one document among several that a premises manager will keep. It sits naturally beside the visitor access log, the card issue and return register, and the alarm user code plan, because all four answer the same question: who is allowed in, and how do we know when that changes.

It also connects to the camera side of the site. If the door with the smart lock is covered by a camera, the register and the recording schedule should agree on what the door area looks like and when it is recorded. Eyonic Security Systems plans, supplies and installs CCTV security systems with camera placement, recording and remote viewing for homes, offices, shops and industrial sites, and a door that is being monitored is a door whose access record is worth keeping accurate. The register does not need camera detail, but the two documents should not contradict each other about which door is which.

For a business deciding between a standalone lock and a panel, the review step described earlier is the right place to settle the register format. If the site later grows into an access control system with many cardholders, the register can grow with it, provided the columns were chosen sensibly at the start.

Keep the register with the other handover documents, and make it part of the handover when a manager changes. A register that lives only in one person's laptop does not survive turnover, which is the exact problem it was meant to solve.

A Short Pre-Handover Check

Before you sign off a smart lock installation, run this short check. It is an author checklist, not a standard.

Does the register exist, and is there one authoritative copy? Is every active user slot on the lock matched to a row? Does every row have a named holder and a removal trigger? Are the admin holders recorded and limited to the number you intended? Is the backup entry method written down and verified, not assumed? Has at least one removal been tested end to end? Is there a named person responsible for the monthly sweep?

If the answer to any of these is no, the lock is installed but the access is not yet managed. The gap is usually small and fixable, and it is much easier to fix while the installer is still on site and the admin menu is open.

For sites in Sarawak planning this kind of work, the practical next step is to settle the register format before the hardware is chosen, then confirm the door condition, user roles and backup method with the supplier. That order keeps the document and the device aligned, and it means the first staff departure after installation is a routine row closure rather than an improvised scramble.
